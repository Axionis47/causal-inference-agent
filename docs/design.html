Causal Agent Design

A general causal analysis agent. It takes a complete context pack and a question, reasons about which family of analysis the data supports, hands off to a library specialist, and returns a report where every claim points at an artifact. High level first, detail spec under each level.

L0Principles

Five rules that every level below obeys. If a later decision breaks one of these, the decision is wrong.

Model decides, harness verifiesReasoning is the model's. The harness checks citations and consistency, never routes by if-else.
No human after the packThe context pack is complete on hand-over. Downstream agents reason from it alone.
Pack is method-freeIt describes what the data is and how it came to be. No treatment, outcome, confounder vocabulary.
Family before libraryA library-free agent decides the analysis family. Specialists never decide whether they apply.
Artifacts are the contractEvery agent reads and writes typed, lineage-tracked artifacts. Head and tail are designed against them.
Detail spec

What "verify, not route" means

When an agent claims "difference-in-differences is possible because banner_flag switched inside users after 14 May," the harness checks that the cited pack fields exist and say that. It does not compute whether DiD is possible. Preconditions are method knowledge stated in the method ontology, read by the model, not evaluated as booleans.

What stays structural

  • Artifact schemas and lineage, so reasoning is inspectable and reusable.
  • Gates as verifiers: a DAG has no cycle, an adjustment set has no descendant of the cause, every citation resolves.
  • Bounds on autonomy: the revision cap and the lane lock.
  • Ontologies as data, not prompt text, so knowledge is versioned and citable.

How it gets smarter

  • The method ontology is extensible by the model; new knowledge is proposed with a source and reviewed in.
  • Thresholds are proposed per design with a justification, stored before the estimate runs, and calibrated by evals.
  • Rulings become facts the model reasons over next time, not new code paths.

L1System

Pack and question in. A design agent works out the family. A branch sends the decision to one specialist. Only the DoWhy specialist is built in phase 0; the others are declared so the branch is honest from day one.

Detail spec

Two agents, one hand-off

The design agent stops when it can write the hand-off and nothing more. The specialist receives the hand-off, the pack, and its own library skill. It never sees the design agent's alternatives or other specialists.

HANDOFF
  family        adjustment | diff_in_diff | discontinuity | instrument | series | root_cause
  outcome       column name
  treatment     column name        (absent for root_cause)
  time_window   from the question, or full coverage
  pack_ref      dataset id + version
  frame_ref     QUESTION_FRAME artifact id
  reasons[]     each with pack field citations

What the specialist may and may not change

  • May: graph, column roles, adjustment set, estimator, refuters, thresholds, target population.
  • May not: family, treatment, outcome, time window, dataset. If it concludes one is wrong, it hands back with a reason and the design agent re-frames.

In LangGraph

Parent graph: design agent, conditional edge on family, one node per specialist, report. Each specialist is a subgraph with its own state and checkpointer scope, so its inner loop and context stay inside the box. Studio shows the parent, and a box opens to the specialist.

L2Context pack

The input payload. Independent of any question and any method. It answers five things about a dataset: what a row is, what each column means and whether it was measured or set, what rule set it, what changed and who got the change, and what the odd values mean.

An organiser agent, built later, turns messy inputs into this. Downstream agents assume it is complete.

Completeness

Every required field on the dataset card. Every CSV column has a card with every required field. set_by present wherever obtained_by demands it. Every observed sentinel has a meaning. Every change in the time span has all fields. Every stated line has a source. The organiser verifies this itself.

Detail spec · querying

Key-based is primary and, for a typical dataset, sufficient. Ten to fifty columns and a handful of changes is a few hundred facts, which fits in context whole. The design agent reads the pack up front and pulls by key when it needs a fact to cite.

get(subject, field)            one fact                "what sets banner_flag"
about(subject)                 every fact on a card
where(field, value)            subjects matching        "which columns are set_by_system"
uses(column)                   columns whose set_by inputs include it
between(start, end)            changes in a window
as_of(subject, field, date)    value valid on a date, for changed definitions
find(text)                     semantic, returns card ids to read, never cited
digest()                       one page of prose, first read

Semantic search is less reliable for exactly the facts that matter most. "What sets banner_flag" must return the one rule or nothing. A near-miss is not an answer. So search finds cards; lookup reads fields; only fields are cited.

Why it serves every family without method words

  • Adjustment reads set_by chains and captured_when.
  • Difference-in-differences reads rollout_shape, who_got_it, time_coverage, entity_interaction.
  • Discontinuity reads rollout_shape = threshold and the criterion, which names the running column and cutoff.
  • Instrument reads rollout_shape = random or a decided_by unrelated to the outcome mechanism.
  • Series reads rollout_shape = all_at_once, dense time_coverage, definition_changes.
  • Root cause reads set_by across all columns, chained, which is a dependency graph in mechanism form.

L3Design agent

Reads the pack and the question. Works out what the question is really asking, what the outcome column is, what could count as the cause, and which family of analysis the data supports. Writes the decision with reasons that cite pack fields. Owns no library and never will.

Detail spec

Step 1 · frame the question

Treatment and outcome columns are not named in the question. The agent proposes them.

  • Intent: effect of a change · driver search · root cause. A question with no identifiable change routes to driver search, whose output is candidate causes for a second, linked run.
  • Outcome: the question names a metric in words. Match against column meanings and the glossary; pick the top if the margin is clear.
  • Cause candidates, from four sources: change words in the question, change cards in the window, columns with obtained_by = set_by_*, and structural signals from the profile. Score by how many sources name it, never by correlation with the outcome.
QUESTION_FRAME
  intent               effect_of_change | driver_search | root_cause
  outcome              converted            cites column:converted.meaning, glossary
  cause_candidates[]   {column, sources[], score}
  time_window
  reasons[]            each with fact ids

Step 2 · decide the family

The agent reasons over the pack's fields directly. What it reads and what it implies:

readsbears on
change card rollout_shape, who_got_itstaggered points to diff-in-diff, threshold to discontinuity, random to instrument, all-at-once on one unit to series
set_by inputs of the cause columnwhere confounding lives; whether adjustment is on the table
captured_when on every columnwhat must be excluded as downstream
time_coverage before and after the changewhether time-based families are possible
entity_interactionwhether cross-entity comparisons are clean
FAMILY_DECISION
  family               adjustment | diff_in_diff | discontinuity | instrument | series | root_cause
  admissible[]         every family the data supports, with reasons and fact ids
  chosen               one of admissible, with the assumption it bets on
  rejected[]           each with the pack field that ruled it out
  supported_now        true | false     (false → report says so, reasons preserved)

Verification, not routing

The harness checks every cited fact id exists and that the field's value is consistent with the claim. It does not recompute the decision. A decision with a broken citation is rejected and the agent retries.

Where specialist thinking shows here

  • Recognising "why did conversion drop" has no change and needs driver search.
  • Noticing "the new pricing" is three change cards and picking the one whose window matches.
  • Rejecting a candidate because its first_active is after the drop.
  • Weighing parallel trends against measured confounding when both families are admissible, and writing which assumption it finds more believable for this system.

L4Specialists

One specialist per family. Each speaks only its library's terms, receives only the hand-off and the pack, and turns the decision into a runnable experiment. Phase 0 builds the DoWhy specialist for the adjustment family. The rest are declared.

adjustment built · phase 0DoWhy. Model, identify, estimate, refute.
diff_in_diff declaredpyfixest. Two-way fixed effects, staggered, event study.
discontinuity · series declaredCausalPy. Regression discontinuity, synthetic control, interrupted series.
heterogeneity declaredEconML. Double ML, causal forests, policy trees. Last, because it is deepest.
root_cause declaredDoWhy GCM. Mechanism per node, attribution.
Detail spec · DoWhy specialist

Pre-flight, before any reasoning

Deterministic checks on the data the moment the hand-off arrives: cause and outcome columns exist and are not all null, the cause takes at least two values with a minimum count each, sample size above a floor, every column in the cause's set_by chain exists, rough overlap between arms. Writes FEASIBILITY. runnable = false hands back at once with named blockers. Seconds, no model call.

When "not runnable" is discovered

  • Design agent, from the pack alone: cause does not vary, its inputs are not in the data, outcome captured before cause. Rejected before hand-off.
  • Pre-flight: the data checks above.
  • Model: every candidate confounder is post-treatment, or the cause's inputs are all unmeasured.
  • Identify: DoWhy returns no set after one in-lane revision.
  • Estimate and diagnose gates: non-finite value, interval does not bracket, pre-registered checks fail after the revision budget.

Every case produces a partial report with the reasons. Library errors become FAILURE artifacts, never silent skips.

Model

Build the graph from the pack. Every set_by input edge becomes a candidate edge tagged mechanism. Assign each column a role in DoWhy's vocabulary: confounder, mediator, collider, effect modifier, post-treatment, ignore. captured_when = after forces post-treatment. The graph is built with NetworkX, gated (acyclic, contains cause and outcome, every edge sourced), and only then serialised to GML for DoWhy.

Identify

Call identify_effect with proceed_when_unidentifiable=False. DoWhy searches for a set that blocks every path into the cause and contains no descendant of it. Gate: the returned set agrees with the roles assigned and every variable exists in the data. No set → revise within the lane, or hand back "not identifiable as adjustment."

Estimate

Choose from the lane's list in fallback order: regression adjustment, propensity weighting, double ML. Choice cites outcome type and sample size. Target population stated. Thresholds for every planned check are written now.

Refute

Placebo treatment, random common cause, data subset, sensitivity to a hidden confounder. Each compared to its pre-registered threshold. Balance and overlap computed alongside.

Revisions allowed inside the lane

  • Add a measured confounder from the pack's set_by chain.
  • Next estimator in the list.
  • Trim to common support.
  • Change target population.
  • Change outcome model form.

Hand-back conditions

  • An effect appears before the change in time, which the adjustment lane cannot fix.
  • The sensitivity bound says a hidden confounder weaker than any measured one erases the effect, and no more variables are available.

Detail spec · what a lane declares

Lanes are configuration. The loop, the lock, and the generic identify, estimate, diagnose nodes are written once. A lane file says:

  • identification mode: graph-based or rule-based, and the rule
  • what it needs from the pack, as method knowledge the model reads
  • estimators in fallback order, each mapped to an adapter
  • checks required, each mapped to an adapter
  • revisions allowed inside the lane
  • hand-back conditions

Adding a lane costs one file, one or two adapters, and an eval set. The fifth lane should be a day.

Scope rule for any library

A capability node must be something you would write in a report's methods section. Everything else is an adapter default. EconML's thirty estimators become four actions with two or three enums each.

L5Artifacts & gates

Storage

One prefix per run, one folder per producer, a run manifest listing every artifact and its parents. Local filesystem now; Cloud Storage with the same layout by flipping one setting. Graph state holds references only, never payloads.

Failure isolation

A node that fails writes a FAILURE record and raises. LangGraph checkpoints the state before it, so upstream artifacts survive and a retry reuses them by hash.

L6Observability & evals

Every agent step is a LangSmith span with the artifact ids it read and wrote. Everything around the agents, the store, the adapters, the API, goes to Logfire. One trace id links both. Golden questions with planted effects on synthetic data are the tail specification made executable.

Detail spec

Traces

  • Span per node, tagged with run id, artifact ids in and out, lane.
  • LLM calls carry the artifact ids they cited, so a bad citation is findable from the trace.
  • Logfire auto-instruments FastAPI, httpx, and the storage client. OpenTelemetry on both sides.

Evals

  • Framing: did the design agent pick the outcome and cause a specialist would, on ten golden questions across three or four domains.
  • Family: did it choose the admitted family and cite the right fields.
  • End to end: did the report recover the planted effect within tolerance, and did diagnostics flag the planted violations.
  • Any change to the ontology, a prompt, or a lane runs the set. A drop fails the change.

L7Stack & phases

LangGraph for the graph, LangSmith for agent traces, Logfire for the rest, Gemini on Vertex AI as the model, Cloud Storage for artifacts. Local first. Four libraries, one per phase.
